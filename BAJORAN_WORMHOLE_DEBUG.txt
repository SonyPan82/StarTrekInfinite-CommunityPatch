CRASH PRÉ-EXISTANT IDENTIFIÉ ET CORRIGÉ (2026-05-09)
================================================================================

CPlanet::UpdateUnhabitableTriggeredModifiers SIGSEGV
  Crash dans le daily update parallèle des planètes inhabitables.
  CONFIRMÉ par l'utilisateur: NON LIÉ aux modifications wormhole.
  Présent même sur new game.

CAUSE IDENTIFIÉE:
  12 jobs vanilla Infinite ont des `triggered_planet_modifier` avec
  des accès `owner = {...}` ou `planet = {...}` SANS `exists = owner` ou
  `exists = planet` en garde. Quand le moteur évalue ces modifiers sur
  des planètes inhabitables (où owner = null), null pointer dereference.

  Jobs concernés (vanilla, non gardés):
  - 100_hornblower_generic_jobs.txt: artisan, purge
  - 101_hornblower_ufop_jobs.txt: security_officer_ufop
  - 102_hornblower_klingon_jobs.txt: high_cleric_klingon, martial_artist_klingon,
    imperial_guardian_klingon, follower_of_kahless_klingon
  - 103_hornblower_cardassian_jobs.txt: inquisitor_cardassian, redactor_cardassian
  - 104_hornblower_romulan_jobs.txt: praetorian_guard_romulan

CORRECTIF APPLIQUÉ:
  Création de common/pop_jobs/zz_cp26_pop_job_fixes.txt qui override les 12
  jobs concernés en ajoutant `exists = owner` ou `exists = planet` comme
  première condition dans chaque bloc `potential` problématique.
  18 blocs `triggered_planet_modifier` au total ont été corrigés.

  Le fix est purement défensif: les modifiers s'appliquent aux mêmes pops/
  planètes qu'avant, mais les triggers se court-circuitent si le scope est
  null au lieu de crasher.

RÉ-IMPLÉMENTATION 2026-05-09 — Approche bypass natif (transwarp conduit)
================================================================================

CONTEXTE:
  Après l'approche popup, l'utilisateur a confirmé que le système popup
  marchait (pas de popup s'affichait), mais les flottes retournaient quand
  même en Alpha. Cause: l'auto-pathfinder utilisait le bypass automatique-
  ment, ou les vaisseaux scientifiques avaient des comportements de retour
  via mécanique vanilla.

  L'utilisateur a demandé d'implémenter un système type "transwarp conduit"
  avec animation visible (non instantané). C'est le comportement natif du
  bypass `wormhole` d'Infinite avec animation_time = 1.

NOUVELLE ARCHITECTURE (transwarp visible):
  1. SUPPRESSION DES POPUPS
     Plus de events .300/.310/.320/.330. Plus d'on_entering_system_fleet
     pour téléporter. La traversée passe uniquement par le bypass natif.

  2. CUSTOM BYPASS cp26_bajoran_bypass
     Modelé sur le wormhole vanilla, avec:
     - is_pathfind = no   ← CRUCIAL: l'auto-router ne route PAS à travers
     - animation_time = 1 ← visuel transwarp/wormhole (1 jour)
     - requires_exploration = no ← découverte gérée par notre event chain
     - prerequisites: aucune tech requise
     Conséquence: la flotte ne traverse QUE si le joueur clique
     explicitement le bypass. Plus de retour involontaire.

  3. SPAWN VIA .200 (à la fin du special project)
     spawn_natural_wormhole = { bypass_type = cp26_bajoran_bypass }
     dans Denorios + Idran. link_wormholes pour les connecter.
     add_seen_bypass_type pour le découvreur.

  4. EVENT .10 (fleet hook)
     Quand une flotte d'un empire entre dans Denorios ou Idran et que cet
     empire n'a pas encore vu le bypass, add_seen_bypass_type pour lui.
     Permet à tous les empires d'utiliser le bypass une fois qu'ils l'ont
     visité, pas seulement le découvreur.

  5. IDRAN RESTE SEALED
     sealed_system flag bloque can_enter_system_by_jump.
     Aucun warp/jump direct depuis Alpha vers Idran.
     Le bypass NE PASSE PAS par can_enter_system_by_jump (utilise
     country_can_use à la place), donc le bypass fonctionne malgré sealed.

FLOW JOUEUR:
  1. Survey Denorios
  2. Année 2369+ → popup investigation → projet spécial
  3. Projet complété → bypass spawné dans Denorios + Idran
  4. Joueur ordonne flotte à Denorios

  6. Joueur clique sur l'icône wormhole pour envoyer la flotte

FLOW IA:

HOTFIX 2026-05-09 — Bounce-back immédiat à Idran après téléport (OBSOLÈTE)
================================================================================

SYMPTÔME (rapporté par utilisateur):
  Flotte traverse Denorios → Idran via popup. Dès l'arrivée à Idran, la
  flotte retourne immédiatement à Denorios (popup .330 fire et l'IA/joueur
  clique YES sans avoir le temps de réagir).

CAUSE:
  set_location dans .310 YES déclenche on_entering_system_fleet pour
  l'arrivée à Idran. À ce moment, le flag cp26_wormhole_recently_used n'a
  pas encore été commit (il était posé dans le bloc YES juste avant
  set_location, mais l'évaluation du trigger de .320 se fait dans le même
  tick et voit l'état pré-flag). .320 fire, popup .330 apparaît, IA
  auto-YES → bounce immédiat.

CORRECTIF:
  Le flag cp26_wormhole_recently_used et le cleanup .301 sont maintenant
  posés dans le bloc IMMEDIATE de .300 et .320 (avant même que le popup
  s'affiche). Garantit que le flag est actif pendant toute la durée du
  popup et de la téléportation.

  Trade-off: le flag pose un cooldown 30 jours par flotte, qu'elle
  traverse ou pas. Si la flotte refuse (NO), elle ne pourra pas re-essayer
  avant 30 jours. C'est acceptable comme anti-spam.

  Les options YES de .310 et .330 ne touchent plus au flag — elles font
  seulement le set_location.

  Symétrique côté Gamma → Alpha (.320 → .330).
