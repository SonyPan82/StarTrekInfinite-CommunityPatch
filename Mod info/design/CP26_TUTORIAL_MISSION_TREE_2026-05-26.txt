CP26 - Tutoriel Simple Pour Ajouter Ou Modifier Une Mission D'Arbre
Date: 2026-05-26

But
- Expliquer simplement comment ajouter une mission dans l'arbre de mission.
- Expliquer comment modifier une mission existante sans tout casser.
- Donner une méthode réutilisable pour CP26.

Ce document est volontairement pratique.
- On ne cherche pas à tout expliquer du moteur.
- On cherche à faire des missions CP26 propres, lisibles et maintenables.

==================================================
2. Anatomie minimale d'un nœud de mission
==================================================

Une mission ressemble à ça :

```txt
qt_example_node = {
    position = { x = 1 y = 1 }

    potential = {
        has_country_id = ufop
    }

    parents = {
        qt_example_parent
    }

    dotted_parents = {
        qt_example_thematic_link
    }

    blocked_by = {
    }

    possible = {
        has_quest_tree_node = qt_example_parent
        has_country_flag = some_flag
    }

    on_started = {
    }

    on_blocked = {
    }

    on_finished = {
        add_resource = {
            unity = 1000
        }
    }

    modifier = {
    }

    ai_weight = {
        factor = 1000
    }
}
```

Les blocs importants :

- `position`
  - place le nœud visuellement dans l'arbre

- `potential`
  - définit pour qui le nœud existe
  - ex: Fédération seulement, Cardassien seulement

- `parents`
  - les nœuds précédents obligatoires
  - c'est ce qui relie le nœud au reste de l'arbre

- `dotted_parents`
  - connexion visuelle en pointillé vers un autre nœud
  - ne rend PAS le nœud inaccessible si ce parent n'est pas accompli
  - utilisé pour indiquer un lien thématique ou narratif sans en faire un prérequis
  - exemples dans CP26 : qt_cardassian_d1, qt_ufop_d1, qt_cardassian_c1, qt_ufop_e1

- `blocked_by`
  - permet d'empêcher un nœud si un autre a été pris ou validé
  - utile pour des branches exclusives

- `possible`
  - les conditions réelles de validation
  - c'est le coeur du nœud

- `on_started`
  - effet quand le nœud commence
  - utile pour poser un flag, lancer un event, initialiser un compteur

- `on_finished`
  - récompense / effet quand le nœud est validé

- `modifier`
  - bonus permanent ou temporaire tant que le nœud est actif/terminé selon le système

- `ai_weight`
  - intérêt de l'IA pour ce nœud


==================================================
3. Ajouter une nouvelle mission
==================================================

Méthode simple et saine :

Etape 1 - copier un nœud proche de ce qu'on veut
- Si c'est un nœud simple à condition directe :
  - copier un nœud de type `possible = { has_flag / has_technology / owns_system }`
- Si c'est un nœud avec compteur :
  - copier un nœud avec `set_variable` / `check_variable`
- Si c'est un nœud narratif :
  - copier un nœud qui déclenche un event dans `on_finished`

Etape 2 - lui donner une nouvelle clé unique
- exemple :
  - `qt_ufop_upgrade_utopia_planitia_a500`
  - `qt_romulan_shadow_network`
  - `qt_cardassian_secure_bajor`

Règle :
- la clé du nœud doit être unique parmi tous les fichiers de common/quest_tree_nodes/
- le nom du fichier n'a aucun rapport avec la clé du nœud
- un seul fichier peut contenir un ou plusieurs nœuds
- exemple concret : qt_ufop_d2.txt contient le nœud qt_ufop_liberate_the_oppressed

Etape 3 - placer sa position
- exemple :
  - `position = { x = 10 y = 4 }`

Conseil :
- ne fais pas ça au hasard
- regarde les voisins dans l'arbre
- garde une progression lisible de haut en bas ou de gauche à droite

Etape 4 - brancher les parents
- c'est ce qui décide quand le nœud devient accessible

Exemple :
```txt
parents = {
    qt_ufop_upgrade_the_enterprise
}
```

Si tu oublies ça :
- le nœud peut apparaître n'importe comment
- ou devenir orphelin dans l'arbre

Etape 5 - écrire la condition `possible`
- c'est ici qu'on met :
  - drapeaux
  - technos
  - possession de systèmes
  - variables
  - compteurs
  - nœuds déjà accomplis

Exemple simple :
```txt
possible = {
    has_quest_tree_node = qt_ufop_upgrade_the_enterprise
    has_country_flag = cp26_a500_utopia_modernization_unlocked
}
```

Exemple avec compteur :
```txt
custom_tooltip = {
    success_text = some_success_loc
    fail_text = some_fail_loc

    check_variable = {
        which = some_counter
        value >= 3
    }
}
```

Etape 6 - écrire la récompense dans `on_finished`
- exemples :
  - `add_research_option = tech_xxx`
  - `country_event = { id = cp26_example.1 }`
  - `add_resource = { unity = 1000 influence = 250 }`
  - `add_modifier = { modifier = nom_du_modifier days = 3600 }`
  - `set_country_flag = mon_flag`

Etape 7 - ajouter la localisation
- au minimum :
  - nom du nœud
  - description
  - tooltips de succès/échec si utilisés

Sans loc :
- le joueur voit des clés brutes


==================================================
4. Modifier une mission existante
==================================================

Quand on modifie un nœud existant, il faut rester méthodique.

Toujours vérifier ces 5 points :

1. `parents`
- si tu changes la place logique du nœud, mets à jour ses parents

2. `possible`
- c'est là que les bugs les plus fréquents se glissent
- surtout si tu touches :
  - flags
  - event targets
  - variables
  - technos

3. `on_started`
- si le nœud initialise un compteur ou un flag, ne supprime pas ça sans réfléchir

4. `on_finished`
- vérifie que la récompense correspond encore au nouveau design

5. localisation
- si le design a changé, le texte joueur doit changer aussi


==================================================
5. Les 3 grands types de missions CP26
==================================================

Type A - Mission simple à condition directe

Exemple :
- contrôler un système
- posséder une techno
- avoir un flag

Forme typique :
```txt
possible = {
    has_technology = tech_example
}
```

C'est le plus simple.


Type B - Mission à compteur

Exemple :
- avoir 3 colonies avec un modifier
- avoir X systèmes
- avoir X pops assimilées

Forme typique :
```txt
on_before_possible = {
    set_variable = {
        which = my_counter
        value = 0
    }

    every_owned_planet = {
        limit = { has_planet_flag = my_flag }
        owner = {
            change_variable = {
                which = my_counter
                value = 1
            }
        }
    }
}

possible = {
    custom_tooltip = {
        success_text = my_success
        fail_text = my_fail

        check_variable = {
            which = my_counter
            value >= 3
        }
    }
}
```

C'est exactement le bon pattern quand on veut compter quelque chose proprement.


Type C - Mission narrative

Exemple :
- déclencher un arc
- débloquer une crise
- ouvrir une suite d'events

Forme typique :
```txt
on_finished = {
    country_event = { id = cp26_example.1 }
}
```

Très utile pour :
- Mars
- Bajor
- branches espionnage
- déblocages de prototypes


==================================================
6. Quand faut-il un event, quand faut-il un nœud ?
==================================================

Utilise un nœud d'arbre si :
- c'est un objectif politique / stratégique durable
- le joueur doit le voir dans sa progression
- tu veux un suivi visible dans l'arbre

Utilise un event si :
- c'est une scène narrative
- un choix ponctuel
- une conséquence
- une réaction

Utilise les deux ensemble si :
- le nœud représente le grand objectif
- et l'event représente la scène ou la récompense

Exemple propre :
- nœud :
  - "Modernisation d'Utopia Planitia"
- event à la fin :
  - "les nouveaux prototypes peuvent maintenant être étudiés"


==================================================
7. Bon pattern pour ajouter une mission de classe de vaisseau
==================================================

Si une mission doit débloquer une classe ou une technologie :

Pattern recommandé

```txt
possible = {
    has_quest_tree_node = qt_previous_node
    has_country_flag = cp26_shipyard_ready
}

on_finished = {
    add_research_option = tech_new_ship_unlock
}
```

Pourquoi c'est bien :
- la mission ne donne pas forcément la techno gratuitement
- elle la rend juste recherchable
- donc le joueur garde un petit rythme techno

Don direct conseillé seulement si :
- la classe existe déjà au départ
- ou si l'event représente une récupération complète de schémas prêts à produire


==================================================
8. Bon pattern pour une mission à choix exclusifs
==================================================

Si tu veux deux branches qui s'excluent :

```txt
blocked_by = {
    qt_other_branch
}
```

Et sur l'autre nœud :

```txt
blocked_by = {
    qt_this_branch
}
```

Comme ça :
- une branche ferme l'autre
- le joueur comprend qu'il choisit une direction


==================================================
9. Erreurs fréquentes à éviter
==================================================

1. oublier la localisation
- résultat :
  - clés brutes visibles

2. oublier `parents`
- résultat :
  - nœud orphelin
  - ordre de progression cassé

3. mettre trop de logique dans `possible`
- si ça devient énorme, il vaut mieux :
  - préparer un flag
  - ou utiliser une variable calculée avant

4. dépendre de `event_target` fragiles sans re-bootstrap
- si un nœud dépend d'un pays/système précis, mieux vaut être sûr que la cible existe

5. mélanger objectif long terme et scène narrative dans un seul bloc
- mieux :
  - nœud = objectif
  - event = scène


==================================================
10. Méthode CP26 recommandée
==================================================

Quand on veut ajouter une mission dans CP26 :

1. écrire d'abord le rôle du nœud en une phrase
2. décider son parent
3. décider si c'est :
   - direct
   - compteur
   - narratif
4. créer le fichier du nœud
5. créer les locs
6. brancher la récompense
7. tester en jeu

Phrase test utile :
- "Qu'est-ce que le joueur doit faire ?"
- "Comment le jeu sait qu'il l'a fait ?"
- "Que gagne-t-il quand c'est validé ?"

Si tu réponds clairement à ces 3 questions, le nœud sera généralement propre.


==================================================
11. Checklist rapide avant validation
==================================================

- Le nœud a une clé propre
- Le fichier est dans `common/quest_tree_nodes/`
- La position est cohérente
- Les parents sont bons
- `possible` reflète bien l'objectif réel
- `on_finished` donne la bonne récompense
- Les locs FR/EN existent
- Le nœud ne court-circuite pas une autre branche sans le vouloir


==================================================
12. Règle d'or
==================================================

Une mission d'arbre n'est pas un event amélioré.

Une bonne mission d'arbre :
- représente un objectif clair
- reste visible dans la progression
- a un parent logique
- a une récompense propre

Si un ajout ne respecte pas ça, mieux vaut en faire un event ou un projet spécial à la place.
