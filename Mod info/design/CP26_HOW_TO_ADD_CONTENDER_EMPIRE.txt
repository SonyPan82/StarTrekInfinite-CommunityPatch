CP26 — GUIDE : AJOUTER UN EMPIRE SPÉCIAL
========================================
Références :
- Orion / Tholian / Gorn / Breen = pattern `contender`
- Ferengi Alliance (2026-05-17) = pattern `country_type` dédié

IMPORTANT :
Ne pas partir du principe que tout nouvel empire spécial doit utiliser
`type = contender`.

`contender` convient aux puissances régionales visibles, belliqueuses, et déjà
intégrées au gameplay de guerre / diplo spécial.

Pour un empire qui doit :
- rester caché avant contact,
- utiliser un premier contact plus vanilla-like,
- éviter certains effets de bord `contender`,

il vaut mieux créer un type dédié (cas Ferengi).

RÈGLE ABSOLUE : ne jamais modifier les fichiers hors du dossier CP26/.
Les fichiers du jeu de base et d'Infinite sont en lecture seule.

CHOIX DU TYPE DE PAYS — RÈGLE DE DÉCISION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Utiliser `type = contender` si :
- l'empire doit être visible tôt,
- l'empire doit jouer comme une vraie puissance régionale agressive,
- l'empire doit partager les mêmes règles que Orion / Gorn / Tholian / Breen.

Créer un type dédié si :
- l'empire doit rester caché avant contact,
- l'empire doit utiliser une découverte / analyse plus vanilla-like,
- l'empire ne doit pas apparaître trop tôt dans la diplomatie,
- l'empire a une économie, une IA ou une logique de guerre qui diverge du bloc contender.

Cas Ferengi (recommandation retenue) :
- type dédié `ferengi_alliance`
- `observable = no`
- `show_in_contacts_list = no`
- `show_borders_in_us = no`
- `standard_diplomacy_module = { contact_rule = does_first_contact_sites }`

Conclusion pratique :
- ne pas “tordre contender” pour un seul empire ;
- préférer un type dédié dès que le comportement visé n'est plus celui d'une
  puissance contender standard.

PIÈGE CRITIQUE — DUPLICATION D'IDENTITÉ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Si un ancien initializer / enclave / vieux prototype existe déjà pour la même
espèce ou la même faction :
- vérifier qu'il n'utilise PAS le même `country_id`
- vérifier qu'il ne réutilise PAS le même flag principal

Exemple de bug réel rencontré :
- vieux bloc Ferengi XuraCorp utilisait `country_id = "ferengi"`
- et `set_country_flag = ferengi`
- résultat : collision potentielle avec la vraie Alliance Ferengi

Bonne pratique :
- donner un `country_id` distinct (`ferengi_xuracorp`)
- donner un flag distinct (`ferengi_xuracorp`)
- éviter les alias ambigus

PIÈGE CRITIQUE — late_init_effect non fiable
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Dans cette version du moteur (Garrett 1.0.7), le late_init_effect de
l'initializer système n'est PAS toujours appelé pour les empires contenders
spawné via setup_scenarios. Cela se manifeste comme suit :
- L'init_effect s'exécute entièrement (pays créé, espèce créée) ✓
- Le late_init_effect (set_owner, create_starbase) ne tourne jamais ✗
- Résultat : pays créé dans les logs, planète vide, empire invisible

SOLUTION OBLIGATOIRE : créer un événement on_game_start (pattern Orion).
L'événement on_game_start est déclenché APRÈS toute l'initialisation et
est garanti d'exécuter. C'est là que se fait le vrai setup de la capitale.

NE PAS mettre dans l'initializer :
- create_ship_design / add_ship_design → peut avorter le late_init_effect
  (source : debug Ferengi 2026-05-17, FRG2 apparaît mais FRG3 absent)

NOTE FERENGI (2026-05-17)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Le premier essai Ferengi en `contender` a montré plusieurs problèmes :
- empire visible trop tôt,
- frontières visibles avant découverte,
- logique de contact pas assez vanilla-like,
- couplage inutile avec le bloc `contender`.

Solution retenue :
- création d'un type dédié `ferengi_alliance`
- retrait du vrai Ferengi du type `contender`
- conservation d'un vieux bloc XuraCorp seulement après renommage
  (`country_id = "ferengi_xuracorp"`, flag dédié)

Leçon :
si le design visé s'écarte déjà du comportement `contender`, il faut arrêter
très tôt de s'acharner et faire un type de pays propre.
