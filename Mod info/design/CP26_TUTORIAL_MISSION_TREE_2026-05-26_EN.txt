CP26 - Simple Tutorial for Adding or Modifying a Mission Tree Node
Date: 2026-05-26

Goal
- Explain simply how to add a mission to the mission tree.
- Explain how to modify an existing mission without breaking anything.
- Provide a reusable method for CP26.

This document is intentionally practical.
- We are not trying to explain the entire engine.
- We are trying to make CP26 missions clean, readable, and maintainable.


==================================================
1. Where is a mission located?
==================================================

In CP26, a mission tree node is generally found in:
- common/quest_tree_nodes/

Useful examples already present:
- qt_ufop_upgrade_utopia_planitia_a500.txt
- qt_ufop_upgrade_enterprise_odyssey.txt
- qt_ufop_d2.txt

The text displayed to the player is then found in:
- localisation/french/
- localisation/english/


==================================================
2. Minimal anatomy of a mission node
==================================================

A mission looks like this:

```txt
qt_example_node = {
    position = { x = 1 y = 1 }

    potential = {
        has_country_id = ufop
    }

    parents = {
        qt_example_parent
    }

    blocked_by = {
    }

    possible = {
        has_quest_tree_node = qt_example_parent
        has_country_flag = some_flag
    }

    on_started = {
    }

    on_blocked = {
    }

    on_finished = {
        add_resource = {
            unity = 1000
        }
    }

    modifier = {
    }

    ai_weight = {
        factor = 1000
    }
}
```

The important blocks:

- `position`
  - places the node visually in the tree

- `potential`
  - defines who the node exists for
  - e.g.: Federation only, Cardassian only

- `parents`
  - the required preceding nodes
  - this is what connects the node to the rest of the tree

- `blocked_by`
  - prevents a node if another has been taken or completed
  - useful for exclusive branches

- `possible`
  - the actual validation conditions
  - this is the core of the node

- `on_started`
  - effect when the node begins
  - useful for setting a flag, firing an event, initializing a counter

- `on_finished`
  - reward / effect when the node is validated

- `modifier`
  - permanent or temporary bonus while the node is active/completed depending on the system

- `ai_weight`
  - AI interest in this node


==================================================
3. Adding a new mission
==================================================

Simple and clean method:

Step 1 - copy a node close to what you want
- If it is a simple node with a direct condition:
  - copy a node of type `possible = { has_flag / has_technology / owns_system }`
- If it is a counter node:
  - copy a node with `set_variable` / `check_variable`
- If it is a narrative node:
  - copy a node that fires an event in `on_finished`

Step 2 - give it a new unique key
- examples:
  - `qt_ufop_upgrade_utopia_planitia_a500`
  - `qt_romulan_shadow_network`
  - `qt_cardassian_secure_bajor`

Rule:
- the filename and the node key must stay consistent

Step 3 - set its position
- example:
  - `position = { x = 10 y = 4 }`

Advice:
- do not place it randomly
- look at the neighbors in the tree
- keep a readable progression from top to bottom or left to right

Step 4 - wire the parents
- this decides when the node becomes accessible

Example:
```txt
parents = {
    qt_ufop_upgrade_the_enterprise
}
```

If you forget this:
- the node may appear out of nowhere
- or become an orphan in the tree

Step 5 - write the `possible` condition
- this is where you put:
  - flags
  - technologies
  - system ownership
  - variables
  - counters
  - already completed nodes

Simple example:
```txt
possible = {
    has_quest_tree_node = qt_ufop_upgrade_the_enterprise
    has_country_flag = cp26_a500_utopia_modernization_unlocked
}
```

Counter example:
```txt
custom_tooltip = {
    success_text = some_success_loc
    fail_text = some_fail_loc

    check_variable = {
        which = some_counter
        value >= 3
    }
}
```

Step 6 - write the reward in `on_finished`
- examples:
  - `add_research_option = ...`
  - `country_event = { id = ... }`
  - `add_resource = { ... }`
  - `add_modifier = ...`
  - `set_country_flag = ...`

Step 7 - add the localisation
- at minimum:
  - node name
  - description
  - success/fail tooltips if used

Without loc:
- the player sees raw keys


==================================================
4. Modifying an existing mission
==================================================

When modifying an existing node, stay methodical.

Always check these 5 points:

1. `parents`
- if you change the logical position of the node, update its parents

2. `possible`
- this is where the most frequent bugs sneak in
- especially if you touch:
  - flags
  - event targets
  - variables
  - technologies

3. `on_started`
- if the node initializes a counter or a flag, do not remove that without thinking

4. `on_finished`
- make sure the reward still matches the new design

5. localisation
- if the design has changed, the player-facing text must change too


==================================================
5. The 3 main types of CP26 missions
==================================================

Type A - Simple mission with a direct condition

Example:
- control a system
- own a technology
- have a flag

Typical form:
```txt
possible = {
    has_technology = tech_example
}
```

This is the simplest.


Type B - Counter mission

Example:
- have 3 colonies with a modifier
- have X systems
- have X assimilated pops

Typical form:
```txt
on_before_possible = {
    set_variable = {
        which = my_counter
        value = 0
    }

    every_owned_planet = {
        limit = { has_planet_flag = my_flag }
        owner = {
            change_variable = {
                which = my_counter
                value = 1
            }
        }
    }
}

possible = {
    custom_tooltip = {
        success_text = my_success
        fail_text = my_fail

        check_variable = {
            which = my_counter
            value >= 3
        }
    }
}
```

This is exactly the right pattern when you want to count something cleanly.


Type C - Narrative mission

Example:
- trigger an arc
- unlock a crisis
- open a chain of events

Typical form:
```txt
on_finished = {
    country_event = { id = cp26_example.1 }
}
```

Very useful for:
- Mars
- Bajor
- espionage branches
- prototype unlocks


==================================================
6. When to use an event, when to use a node?
==================================================

Use a tree node if:
- it is a lasting political / strategic objective
- the player should see it in their progression
- you want visible tracking in the tree

Use an event if:
- it is a narrative scene
- a one-time choice
- a consequence
- a reaction

Use both together if:
- the node represents the big objective
- and the event represents the scene or the reward

Clean example:
- node:
  - "Utopia Planitia Modernization"
- event at the end:
  - "the new prototypes can now be researched"


==================================================
7. Good pattern for adding a ship class mission
==================================================

If a mission should unlock a class or a technology:

Recommended pattern

```txt
possible = {
    has_quest_tree_node = qt_previous_node
    has_country_flag = cp26_shipyard_ready
}

on_finished = {
    add_research_option = tech_new_ship_unlock
}
```

Why this is good:
- the mission does not necessarily give the tech for free
- it just makes it researchable
- so the player keeps a light tech rhythm

Direct grant recommended only if:
- the class already exists at game start
- or if the event represents a full blueprint recovery ready to produce


==================================================
8. Good pattern for a mission with exclusive choices
==================================================

If you want two branches that exclude each other:

```txt
blocked_by = {
    qt_other_branch
}
```

And on the other node:

```txt
blocked_by = {
    qt_this_branch
}
```

This way:
- one branch closes the other
- the player understands they are choosing a direction


==================================================
9. Frequent mistakes to avoid
==================================================

1. Forgetting the localisation
- result:
  - raw keys visible in-game

2. Forgetting `parents`
- result:
  - orphan node
  - broken progression order

3. Putting too much logic in `possible`
- if it becomes huge, it is better to:
  - prepare a flag beforehand
  - or use a variable calculated before

4. Depending on fragile `event_target` without re-bootstrapping
- if a node depends on a specific country/system, make sure the target exists

5. Mixing long-term objective and narrative scene in a single block
- better:
  - node = objective
  - event = scene


==================================================
10. Recommended CP26 method
==================================================

When you want to add a mission in CP26:

1. First write the role of the node in one sentence
2. Decide its parent
3. Decide if it is:
   - direct
   - counter
   - narrative
4. Create the node file
5. Create the locs
6. Wire the reward
7. Test in-game

Useful test questions:
- "What does the player need to do?"
- "How does the game know they did it?"
- "What do they gain when it is validated?"

If you can answer these 3 questions clearly, the node will generally be clean.


==================================================
11. Quick checklist before validation
==================================================

- The node has a clean key
- The file is in `common/quest_tree_nodes/`
- The position is consistent
- The parents are correct
- `possible` accurately reflects the real objective
- `on_finished` gives the right reward
- FR/EN locs exist
- The node does not short-circuit another branch unintentionally


==================================================
12. Golden rule
==================================================

A mission tree node is not an improved event.

A good mission tree node:
- represents a clear objective
- stays visible in the progression
- has a logical parent
- has a clean reward

If an addition does not follow this, it is better to make it an event or a special project instead.
