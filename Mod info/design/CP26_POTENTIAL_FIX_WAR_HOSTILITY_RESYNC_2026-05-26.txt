CP26 POTENTIAL FIX - WAR HOSTILITY RESYNC
Date: 2026-05-26

Issue observed
- Sometimes an enemy fleet can attack a fleet, station, or starbase but is not fully treated as a valid hostile target.
- Result: one side can fire, while the other side does not properly retaliate.

Probable cause
- This looks like a partial desync between:
  - war state
  - hostility state
  - border/access state
  - target validation in combat
- Part of the bug may be engine-side, but CP26 may still be able to reduce it.

Why CP26 may help
- Infinite exposes hostility logic in script:
  - is_hostile
  - is_hostile_to
  - set_faction_hostility = { set_hostile = yes/no }
- CP26 already has a war-start hook:
  - common/on_actions/zz_cp26_war_access_on_actions.txt
  - events/zz_cp26_war_access_events.txt

Potential fix approach
1. On war start, run a narrow "hostility resync" event.
2. For each direct war participant:
   - reaffirm hostility toward current enemies
   - reaffirm hostility from enemies back toward them
3. Keep this separate from border-opening logic.
4. Do not run this monthly on every country unless absolutely necessary.

Recommended scope
- Trigger only on:
  - on_war_beginning
- Optional follow-up only if needed:
  - rare targeted refresh for special scripted wars, crisis entities, or rebel countries

Why this is preferable
- Low CPU cost if done once at war start
- Minimal risk compared to a continuous galaxy-wide scan
- Matches CP26's current event-driven style

CPU / performance note
- Light version:
  - one event at war declaration
  - likely cheap
- Heavy version:
  - monthly or frequent hostility checks across many countries/fleets
  - likely expensive and not recommended

Limits
- If the actual failure happens inside hardcoded combat target validation, this will not fully fix the bug.
- In that case CP26 can only reduce the chance of the bug, not guarantee its disappearance.

Recommended status
- Worth testing as a targeted CP26 workaround
- Do not treat as a guaranteed full fix
