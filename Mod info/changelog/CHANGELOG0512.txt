[CRASH][HIGH] Fix Denobula colony — même pattern que Vega, deuxième occurrence
  Symptôme : SIGSEGV dans `CConstructionQueueManager::DailyUpdate` après
  ~14 minutes de jeu en partie UFOP. Crash random selon l'AI Denobulan qui
  finit par toucher la queue corrompue. Même signature exacte que le crash
  Vega que tu avais fixé.

  Cause : `events/aacoldenob_events.txt` (event `aa_coldenob.1000`, game start
  UFOP) faisait `create_colony` sur Denobula puis, deux sub-blocs plus loin
  dans `random_owned_planet`, `add_building = building_clinic` au même tick.
  Pattern strictement identique à celui de Vega (`vgcol_events.txt` avant
  ton fix) : la `ConstructionQueue` de la planète est dans un état non
  stabilisé quand `add_building` est commit → corruption silencieuse → SIGSEGV
  quand l'engine itère sur la queue dans un `DailyUpdate` ultérieur.

  Fix : calque du pattern Vega
    • events/aacoldenob_events.txt L54 : `add_building = building_clinic` retiré,
      remplacé par `set_planet_flag = cp26_denobula_needs_clinic`.
    • events/cp26_delayed_capital_upgrade.txt : nouveau bloc `if` dans
      `cp26_capital_upgrade.2`, sibling du bloc Vega :
          if = {
              limit = { has_planet_flag = cp26_denobula_needs_clinic }
              add_building = building_clinic
              remove_planet_flag = cp26_denobula_needs_clinic
          }
      Le clinic est donc commit à J+3 via le même mécanisme que le foundry
      Vega, après stabilisation de la queue par l'engine.

  → Effet en jeu :
     - Denobula garde son clinic dès le tout début de partie (J+3 au lieu de J+0).
     - Plus de crash random `DailyUpdate` lié à la queue Denobula.
     - Lore intact : la Fédération équipe toujours sa colonie avec ce qu'il faut.

[AUDIT][LOW] Audit exhaustif `create_colony` + `add_building` / `remove_building`
  Suite au fix Vega + Denobula, audit complet de tous les patterns à risque
  pour la `CConstructionQueue` dans le mod (events/ + common/scripted_effects/ +
  common/solar_system_initializers/).

  Résultat — TOUS les autres cas sont safe :
    • Remus, Risa, Lunar One, Mars, Trill northern colony :
      `create_colony` seul, sans `add_building` voisin.
    • Setup capitales Tholian / Orion / Gorn / Breen :
      uniquement `add_district_and_planet_size_if_needed_effect` + flag
      `cp26_needs_capital_upgrade` → opérations sensibles routées vers J+3.
    • Breen Secundus, Orion Verex : `create_colony` seul, pas de building immédiat.
    • Solar system initializers Cardassia, Romulus/Glintara,
      20 minor factions (other_owned/*) : aucun `add_building`.
    • `XL_MAP.002` (admin offices UFOP/Klingon) : déclenché via le hook
      moteur `empire_init_capital_planet` après stabilisation complète de
      la capitale (pattern vanilla, safe).
    • `cp26_delayed_capital_upgrade.txt` : la seule occurrence de
      `remove_building` du mod, déjà différée J+3 par construction.

  Cas surveillé (non-fixé) :
    • `common/solar_system_initializers/klingon/klingon_khitomer_initializer.txt:53`
      `late_init_effect = { create_khitomer_colony = yes ; add_building = building_bureaucratic_1 }`
      Pattern syntaxiquement similaire mais sémantiquement différent : tout
      est dans un seul bloc `late_init_effect`, un hook moteur dédié dans
      lequel le moteur garantit l'ordre commit. Vanilla utilise déjà ce
      pattern (`create_khitomer_colony` contient lui-même un
      `add_building = building_capital` interne) sans crash signalé. À
      retirer ou différer si un crash Klingon-spécifique remonte.

[HOTFIX][LOW] Crash SIGSEGV après le load — 3 modifiers research-catégorie invalides
  Symptôme : crash signal 11 (SIGSEGV) dans `CullAndUpdateEntitiesRecursive`
  juste après le passage au tick de gameplay. Stack trace propre côté moteur
  (pas de save corrompue), pointait l'entity system du rendu d'objets.

  Cause réelle (visible dans logs/error.log juste avant le crash) :
    [modifier.cpp:2758]: Invalid modifier planet_jobs_society_research_produces_mult
                         at common/traits/zz_cp26_minor_species_traits.txt line: XX
    (12 occurrences sur 3 noms de modifiers, 9 races impactées)

  Les modifiers `planet_jobs_society_research_produces_mult`,
  `planet_jobs_physics_research_produces_mult`,
  `planet_jobs_engineering_research_produces_mult` apparaissent en clair dans
  les fichiers vanilla STI (`static_modifiers/02_static_modifers.txt`,
  `species_rights/06_species_rights_profiles.txt`) mais **TOUS commentés**.
  Vestiges Stellaris non portés en Star Trek: Infinite — l'engine STI ne sait
  PAS les évaluer et les marque "Invalid". Les traits species qui les
  référencent retournent des modifiers fantômes, ce qui corrompt l'état des
  pops puis casse le rendu d'entités au premier update.

  Fix : remplacement des 12 occurrences par `planet_jobs_research_produces_mult`
  (modifier générique research effectivement supporté par STI, utilisé dans
  `trait_intelligent` et 30+ traits species vanilla). Pour le trait Bajoran
  `trait_selective_researchers_bajoran` qui combinait 2 lignes drawback
  -10% chacune (-20% net), consolidation en une seule ligne -10% pour
  éviter la double pénalisation lors du collapse.

  Fichier modifié :
    common/traits/zz_cp26_minor_species_traits.txt   (12 lignes, 11 traits)
    Mod info/CP26_MINOR_SPECIES_TRAITS.txt           (doc HOTFIX en bas)

  → Effet en jeu :
     - Plus de "Invalid modifier" dans error.log au load.
     - Bonus research conservés en magnitude, généralisés (au lieu d'être
       fléchés society / physics / engineering).
     - Suppression du crash SIGSEGV au premier update entité.

[CRASH][HIGH] Radius galaxie 570 → 500 (limite engine hardcodée)
  Cause racine des crashes aléatoires SIGSEGV / EXC_BAD_ACCESS dans
  CConstructionQueueManager::DailyUpdate et CSaveGameTaskManager::
  CreateMemoryFiles (Mac et Windows — "access violation 0xc0000005" sous
  Windows, KERN_PROTECTION_FAILURE sous macOS).

  Diagnostic :
  Le moteur Clausewitz (commun à Stellaris et Star Trek: Infinite) impose
  une limite HARDCODÉE de radius <= 500. La doc officielle Paradox dit :

    "the map in Stellaris is a box 1000x1000x10, from -500 to +500"
    "Map radius (max 500)"
    "should be less than 500, preferably less than ~460"
    — Stellaris Wiki, Map_modding

  Au-dessus de 500, les structures spatiales internes du moteur
  (quadtree de proximity, grilles pathfinding, indices ConstructionQueue)
  débordent et provoquent des accès mémoire hors zone allouée. Le crash
  apparait au moment où un objet (constructeur, flotte, save serializer)
  tombe dans la zone fantôme — d'où le caractère aléatoire.

  État actuel CP26 :
    - Alpha-Beta_medium.txt : radius = 570  (HORS LIMITE)
    - tutorial.txt           : radius = 570  (HORS LIMITE)
    - Tous les autres scenarios : radius 300/400/450 (OK)

  Mesure géométrique : les 258 positions de systèmes ont une distance
  maximale de 405 depuis l'origine (hypot). Baisser le radius à 460
  garde TOUS les systèmes dans la box avec 55 unités de marge.

  Fix :
    - Alpha-Beta_medium.txt : radius 570 → 500 (engine hard cap exact)
    - tutorial.txt          : radius 570 → 500 (sync)
    - Camera limits inchangées (max abs = 450, déjà dans la box engine)
    - Hypot max système = 405, donc 95 unités de marge sous le cap engine.

  → Effet attendu : élimination des crashes aléatoires
    SIGSEGV/access-violation au runtime et au save. C'est la cause RACINE
    qu'on cherchait depuis le début. Mes diagnostics précédents (queue
    de construction "saturée par le ship_data dynamique", ConstructionQueue
    "corruption script") étaient des amplificateurs au mieux, pas la cause.
    Le radius était bien le problème.

[FIX][LOW] Caméra Galaxy View — systèmes du sud inaccessibles au dézoom
  Symptôme : impossible d'atteindre les systèmes les plus au sud quand
  on dézoome (Romulan, Cardassian, certains minors).

  Cause : les `camera_limit_max_y` étaient calibrés pour les anciennes
  positions de la galaxie. Avec le layout actuel les systèmes vont
  jusqu'à Y=404, mais les limites étaient :
    step 2 : 358   step 3 : 342   step 4 : 327
    step 5 : 312   step 6 : 296   step 7 : 281
  → tous les systèmes Y > 281 devenaient inaccessibles au max zoom out.

  Fix : `camera_limit_max_y` remonté à 440-450 sur les 6 steps de
  zoom-out dans Alpha-Beta_medium.txt et tutorial.txt (synchronisés).

  → Effet : tous les systèmes du sud à nouveau cliquables à tous les
    niveaux de zoom.

[BAL][LOW] B.5 — AI_MAX_DISTANCE 300 → 230
  CP26 portait AI_MAX_DISTANCE à 300 (vanilla 200) pour rendre l'IA plus
  agressive. Mais avec une galaxie de rayon 630, 300 = ~½ galaxie : l'IA
  planifiait des guerres jusqu'à l'autre bout du monde, consommait de la
  CPU pour rien, et contribuait probablement aux crashs
  CConstructionQueueManager::DailyUpdate. Réduit à 230 : plus agressive
  que vanilla, mais reste sur le voisinage.

  → Effet attendu : performances mid/late game améliorées, IA plus
    cohérente géographiquement, réduction du risque de crash construction.
