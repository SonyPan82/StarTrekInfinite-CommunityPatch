[FIX][LOW] Luna One Colony — modifier dupliqué (visuel double sur Luna)
  Symptôme : Luna affichait deux instances du modifier "Lunar One Colony".
  Cause racine, deux problèmes superposés :
    1) Collision de définition. Le modifier `lunar_one_colony` est défini à
       la fois côté vanilla (modifiers chargés tardivement, sans stats, juste
       l'icône) et côté CP26 (`common/static_modifiers/00_aalunmars_static_modifiers.txt`,
       avec les vrais stats : +2 chercheurs, +2 logements, +20%/-20% specialist/worker,
       -50% growth, +25% amenities usage). Pour `static_modifiers`, Clausewitz
       applique "last-loaded-wins", donc vanilla écrasait la définition CP26
       et Luna perdait silencieusement ses stats.
    2) Double application. Vanilla `events/game_start.txt` applique le modifier
       à Luna ET CP26 `events/aalm_events.txt:31` l'applique aussi. Comme les
       deux entrées sont permanentes (`days = -1`), elles s'empilent visuellement.

  Fix appliqué :
    - Renommage `lunar_one_colony` → `lunar_one_colony_cp26` dans
      `common/static_modifiers/00_aalunmars_static_modifiers.txt`.
    - `events/aalm_events.txt:31` applique désormais `lunar_one_colony_cp26`.
    - Ajout des clés de localisation EN/FR pour `lunar_one_colony_cp26`
      (`zz_cp26_patch_l_english.yml`, `zz_cp26_patch_l_french.yml`).

  Résultat in-game :
    - Luna reçoit l'instance vanilla cosmétique (icône uniquement, conservée pour ne
      pas casser le visuel familier).
    - Luna reçoit en plus l'instance CP26 fonctionnelle (vrais stats) avec un
      libellé distinct ("Lunar One Colony").
    - Plus de doublon visuel inutile : la première entrée a son icône et son nom
      vanilla, la seconde porte les bonus chercheurs + logements.

[FIX][LOW] Icons manquantes — 4 species traits Denobulan + Reman
  Symptôme : dans le panel de population et l'éditeur d'espèces, les traits
  `trait_denob_communal`, `trait_denob_polyamorous`, `trait_denob_family`
  (denobulan_traits.txt) et `trait_reman_homeworld` (remus_traits.txt)
  s'affichaient sans icône (carré vide / icône fallback).
  Cause : le moteur cherche par défaut `gfx/interface/icons/traits/<clé>.dds`,
  mais aucun de ces 4 fichiers n'existe (ni en vanilla ni en CP26). CP26 fournit
  6 icônes custom (Risan/Tholian), les 60 traits minor species pointent vers
  des icônes vanilla compatibles, mais ces 4 traits avaient été oubliés.

  Fix appliqué : champ `icon = "..."` ajouté à chaque trait, mappé vers une
  icône vanilla thématiquement cohérente (toutes vérifiées existantes sur disque) :
    - trait_denob_communal       → trait_communal.dds
    - trait_denob_polyamorous    → trait_rapid_breeders.dds
    - trait_denob_family         → trait_traditional.dds
    - trait_reman_homeworld      → trait_pc_nuked_preference.dds
  Zéro nouveau .dds nécessaire, aucun risque sur la chaîne d'assets.

[FIX][LOW] hrb_colony.75 / hrb_colony.83 — passage à replace_path
  Découverte d'aujourd'hui : pour la base de données 'events', Clausewitz
  applique la règle "first-loaded-wins" (eventmanager.cpp:367 logge
  "an event with id [X] already exists!" et IGNORE la nouvelle définition).
  C'est l'INVERSE des autres bases (pop_jobs, ship_sizes, country_types,
  districts, casus_belli...) où c'est "last-wins" via game_singleobjectdatabase.h:151
  qui logge "using the one at..." et garde la NOUVELLE.

  Conséquence : le précédent fix `events/zz_cp26_fix_vanilla_colony_events.txt`
  redéfinissait `hrb_colony.75` et `.83` MAIS chargeait après vanilla, donc
  était systématiquement rejeté. Visible dans error.log :
    [HH:MM:SS][eventmanager.cpp:367]: an event with id [hrb_colony.75]
      already exists!  file: events/zz_cp26_fix_vanilla_colony_events.txt line: 31
    [HH:MM:SS][eventmanager.cpp:367]: an event with id [hrb_colony.83]
      already exists!  file: events/zz_cp26_fix_vanilla_colony_events.txt line: 67
  Les deux bugs scope d'origine (unsupported scope hrb_colony.75 + undefined
  target aqueduct_scientist hrb_colony.83) continuaient donc à se déclencher.

  Solution propre : passage à `replace_path` pour `events/hornblower_colony_events.txt`,
  pattern déjà utilisé pour 3 autres fichiers d'events vanilla
  (hornblower_country_events, hornblower_game_start, hornblower_pirate_events).

  Procédure :
    1. Copie byte-perfect du fichier vanilla (71668 bytes, CRLF préservé,
       MD5 identique en sortie de cp).
    2. Deux patches chirurgicaux appliqués en mode binaire Python pour
       garantir la préservation des line endings CRLF :
       - hrb_colony.75 (ligne 2967) : sortie du `hidden_effect { country_event }`
         hors du bloc `event_target:colony_ruins_uncovered = { ... }`
         (le country_event doit s'exécuter en scope country, pas planet).
       - hrb_colony.83 (ligne 3479) : `event_target:aqueduct_scientist = {...}`
         enveloppé dans `if = { limit = { exists = event_target:... } ... }`
         pour gérer le cas où le special_project upstream n'a pas pu
         capturer le scientifique (leader absent).
    3. Validation : 58 events présents (identique), 112 mentions hrb_colony.*
       (identique), 910/910 accolades équilibrées (vanilla 908/908, +2 paires
       attendues = 1 bloc planet refermé + 1 if/limit ajouté).
    4. Ajout `replace_path="events/hornblower_colony_events.txt"` dans
       descriptor.mod (insertion alphabétique avant les 3 autres events).
    5. Suppression de `events/zz_cp26_fix_vanilla_colony_events.txt`
       devenu redondant — l'ancien fichier provoquait simplement deux
       warnings de chargement, et la logique du fix est désormais portée
       directement dans la copie vanilla.

  Impact en jeu :
    ✓ hrb_colony.75 : la visite de retour J+10 ans après "Bomb Fields"
      (event chain hrb_colony.75001 → .75002) se déclenche à nouveau
      correctement. Plus de scope error logée à chaque option.a choisie.
    ✓ hrb_colony.83 : si le scientifique d'Aqueduct n'a pas été capturé
      en amont, l'option a) reste valide sans logger d'Invalid context
      switch ; le trait Pathologist est appliqué uniquement quand un
      leader existe.
    ✓ error.log : deux warnings "eventmanager.cpp:367 already exists!"
      éliminés au chargement, plus de "unsupported scope hrb_colony.75",
      plus d'"Invalid context switch [event_target:aqueduct_scientist]".

  Maintenance future : si Paradox publie un correctif vanilla de
  hornblower_colony_events.txt (peu probable, STI en maintenance depuis
  2024), il faudra re-merger les changements manuellement. Coût minimal.


[POLISH][LOW] Nettoyage warnings game error.log — 3 fixes appliqués, 3 laissés
  Audit de tous les warnings/script errors visibles dans
  /Documents/Paradox Interactive/Infinite/logs/error.log sur partie longue.
  Tri par cause (CP26 vs vanilla) et faisabilité.

  ─── FIX 1 — zz_cp26_fix_country_events.txt:48 (add_opinion_modifier on oneself) ───
    Notre fichier CP26 dédié au fix de country.27500 (premier contact UFOP)
    avait un check `NOT = { is_same_value = from }` placé au LIMIT racine
    de l'event. Quand le moteur entre dans `fromfrom = { add_opinion_modifier
    = { who = from ... } }`, le scope devient `fromfrom` et la comparaison
    `is_same_value = from` ne réfère plus au scope racine — donc le check
    ne protégeait pas du cas `fromfrom == from`. Résultat : warning
    "Trying to add_opinion_modifier on oneself" à chaque déclenchement
    avec le scope chainé pointant vers le même pays.
    Fix : check `is_same_value` déplacé À L'INTÉRIEUR du scope target
    pour qu'il compare avec le bon contexte. Les deux blocs (from →
    fromfrom et fromfrom → from) ont été durcis symétriquement.

  ─── FIX 2 — Stella Maris / USS Olympia leader scope error ───
    Vanilla `common/special_projects/00_hornblower_colony_projects.txt`
    ligne 36 et 233 fait `on_success = { leader = { save_event_target_as
    = X } }` sans guard. Si le science ship n'a pas de leader assigné
    (réassignement, mort, etc.), `leader = { ... }` lance "Invalid context
    switch [leader] from <ship>" et le target n'est jamais créé.
    L'event consommateur (hrb_colony.83 pour aqueduct_scientist) plante
    ensuite avec "Undefined event target".
    Fix : créé `common/special_projects/zz_cp26_fix_vanilla_colony_projects.txt`
    qui redéfinit les 2 special_projects fautifs (THE_SHADOW_PEOPLE,
    AQUEDUCT_LIFEFORM) avec un wrapper `if = { limit = { exists = leader }
    leader = { ... } }`. Le projet réussit normalement, seul le bonus
    trait scientifique est skippé si le leader manque (au lieu de crasher
    avec un log error).

  ─── FIX 3 — hrb_colony.75 unsupported scope + hrb_colony.83 undefined target ───
    Vanilla `events/hornblower_colony_events.txt` ligne 2978 (hrb_colony.75)
    fait un `country_event = { id = hrb_colony.75001 days = 3600 }` depuis
    le scope planet (`event_target:colony_ruins_uncovered = { ... }`).
    country_event exige scope country → "attempted to execute an effect
    on an unsupported scope". L'event de retour à J+3600 (10 ans) était
    silencieusement perdu.
    Vanilla ligne 3484 (hrb_colony.83 option a) consomme
    `event_target:aqueduct_scientist` sans guard — directement impacté
    par le bug Stella Maris ci-dessus.
    Fix : créé `events/zz_cp26_fix_vanilla_colony_events.txt` qui redéfinit
    hrb_colony.75 (country_event sorti du bloc planet, fired depuis le
    scope country racine) et hrb_colony.83 (event_target:aqueduct_scientist
    wrapped dans `if exists`).

  ─── NON-FIXÉ 1 — Mission AI no positive ai_chance (mission.16/17/55/86/193/215/...) ───
    Symptôme : "Triggered Event mission.X for AI Y has no options with
    positive ai_chance!" déclenché ~10x sur une partie longue pour les
    AI minor factions (Farian, Trill, Bolian, Bajoran, Malcorian,
    Pelian, Kesprytt, etc.).
    Cause : ces events vanilla ont des options avec `trigger = { is_ufop =
    yes }`, `trigger = { is_klingon = yes }` etc. Aucune option ne matche
    pour les minor factions. Le moteur choisit option 0 par défaut.
    Pourquoi maintenant : la session a boosté l'activité des minors
    (species_classes refactor, traits species, AI personalities). Ces
    events back-end leur popent plus souvent qu'avant.
    Pourquoi pas fix : ce sont des events `hide_window = yes` +
    `is_triggered_only = yes`. Le moteur tolère et continue sans crasher.
    Fix possible = filtrer `is_minor = no` au top de mission.213 et 9
    autres events, MAIS risque réel de casser des mission chains qui
    impliquent légitimement les minors. Test exhaustif requis pour
    chaque event, bénéfice nul (le jeu continue, juste du bruit log).

  ─── NON-FIXÉ 2 — First Contact missing (on_action_events.txt:5105) ───
    Symptôme : "<X> has encountered <Y> ... but has neither communications
    with them nor an active First Contact site to do so."
    Cause : le `log_error = "..."` est VOLONTAIRE en vanilla. Le moteur
    log puis fait `establish_communications_no_message = prev` juste après.
    C'est un message de debug intentionnel, pas une erreur fatale.
    Pourquoi pas fix : retirer le log_error demanderait d'override
    `events/on_action_events.txt` (~5000 lignes vanilla). Coût excessif
    pour supprimer un log debug par design. Plus de minors actifs =
    plus de logs, c'est attendu.

  ─── NON-FIXÉ 3 — Spy mission cleanup (spy_mission_spy_global undefined) ───
    Symptôme : "Trying to remove undefined event target: spy_mission_spy_global"
    Cause : `clear_global_event_target = spy_mission_spy_global` est
    appelé dans l'`after` block d'events spy. Si le target n'a pas été
    créé en amont (event chain incomplète), le clear log un warning et
    fait rien.
    Pourquoi pas fix : STI n'expose pas de syntaxe `exists = global_event_target:X`
    pour wrapper proprement. Vanilla utilise ce pattern partout sans
    guard (10+ occurrences anomaly/borg/spy events). Le moteur tolère.
    Fix demanderait reverse-engineering de la spy chain complète pour
    garantir le save préalable.

  Fichiers ajoutés :
    common/special_projects/zz_cp26_fix_vanilla_colony_projects.txt   (Stella Maris + Shadow People)
    events/zz_cp26_fix_vanilla_colony_events.txt                     (hrb_colony.75 + hrb_colony.83)

  Fichier modifié :
    events/zz_cp26_fix_country_events.txt                            (durcissement is_same_value check)

  → Effet en jeu :
    - 3 warnings éliminés du log (CP26 self-opinion, Stella Maris scope,
      hrb_colony.75 scope).
    - Mission chains "Of Klingons and Romulans" et "Stella Maris" arrivent
      désormais à leurs payouts trait/research même si le scientifique
      est absent au moment de l'on_success.
    - L'event return-visit de Planet of Ruins (J+3600) n'est plus perdu.
    - Les 3 warnings non-fixés restent visibles mais documentés comme
      "vanilla intentionnel" ou "fix risqué non rentable".

[CRASH][HIGH] Fix Denobula colony — même pattern que Vega, deuxième occurrence
  Symptôme : SIGSEGV dans `CConstructionQueueManager::DailyUpdate` après
  ~14 minutes de jeu en partie UFOP. Crash random selon l'AI Denobulan qui
  finit par toucher la queue corrompue. Même signature exacte que le crash
  Vega que tu avais fixé.

  Cause : `events/aacoldenob_events.txt` (event `aa_coldenob.1000`, game start
  UFOP) faisait `create_colony` sur Denobula puis, deux sub-blocs plus loin
  dans `random_owned_planet`, `add_building = building_clinic` au même tick.
  Pattern strictement identique à celui de Vega (`vgcol_events.txt` avant
  ton fix) : la `ConstructionQueue` de la planète est dans un état non
  stabilisé quand `add_building` est commit → corruption silencieuse → SIGSEGV
  quand l'engine itère sur la queue dans un `DailyUpdate` ultérieur.

  Fix : calque du pattern Vega
    • events/aacoldenob_events.txt L54 : `add_building = building_clinic` retiré,
      remplacé par `set_planet_flag = cp26_denobula_needs_clinic`.
    • events/cp26_delayed_capital_upgrade.txt : nouveau bloc `if` dans
      `cp26_capital_upgrade.2`, sibling du bloc Vega :
          if = {
              limit = { has_planet_flag = cp26_denobula_needs_clinic }
              add_building = building_clinic
              remove_planet_flag = cp26_denobula_needs_clinic
          }
      Le clinic est donc commit à J+3 via le même mécanisme que le foundry
      Vega, après stabilisation de la queue par l'engine.

  → Effet en jeu :
     - Denobula garde son clinic dès le tout début de partie (J+3 au lieu de J+0).
     - Plus de crash random `DailyUpdate` lié à la queue Denobula.
     - Lore intact : la Fédération équipe toujours sa colonie avec ce qu'il faut.

[AUDIT][LOW] Audit exhaustif `create_colony` + `add_building` / `remove_building`
  Suite au fix Vega + Denobula, audit complet de tous les patterns à risque
  pour la `CConstructionQueue` dans le mod (events/ + common/scripted_effects/ +
  common/solar_system_initializers/).

  Résultat — TOUS les autres cas sont safe :
    • Remus, Risa, Lunar One, Mars, Trill northern colony :
      `create_colony` seul, sans `add_building` voisin.
    • Setup capitales Tholian / Orion / Gorn / Breen :
      uniquement `add_district_and_planet_size_if_needed_effect` + flag
      `cp26_needs_capital_upgrade` → opérations sensibles routées vers J+3.
    • Breen Secundus, Orion Verex : `create_colony` seul, pas de building immédiat.
    • Solar system initializers Cardassia, Romulus/Glintara,
      20 minor factions (other_owned/*) : aucun `add_building`.
    • `XL_MAP.002` (admin offices UFOP/Klingon) : déclenché via le hook
      moteur `empire_init_capital_planet` après stabilisation complète de
      la capitale (pattern vanilla, safe).
    • `cp26_delayed_capital_upgrade.txt` : la seule occurrence de
      `remove_building` du mod, déjà différée J+3 par construction.

  Cas surveillé (non-fixé) :
    • `common/solar_system_initializers/klingon/klingon_khitomer_initializer.txt:53`
      `late_init_effect = { create_khitomer_colony = yes ; add_building = building_bureaucratic_1 }`
      Pattern syntaxiquement similaire mais sémantiquement différent : tout
      est dans un seul bloc `late_init_effect`, un hook moteur dédié dans
      lequel le moteur garantit l'ordre commit. Vanilla utilise déjà ce
      pattern (`create_khitomer_colony` contient lui-même un
      `add_building = building_capital` interne) sans crash signalé. À
      retirer ou différer si un crash Klingon-spécifique remonte.

[HOTFIX][LOW] Crash SIGSEGV après le load — 3 modifiers research-catégorie invalides
  Symptôme : crash signal 11 (SIGSEGV) dans `CullAndUpdateEntitiesRecursive`
  juste après le passage au tick de gameplay. Stack trace propre côté moteur
  (pas de save corrompue), pointait l'entity system du rendu d'objets.

  Cause réelle (visible dans logs/error.log juste avant le crash) :
    [modifier.cpp:2758]: Invalid modifier planet_jobs_society_research_produces_mult
                         at common/traits/zz_cp26_minor_species_traits.txt line: XX
    (12 occurrences sur 3 noms de modifiers, 9 races impactées)

  Les modifiers `planet_jobs_society_research_produces_mult`,
  `planet_jobs_physics_research_produces_mult`,
  `planet_jobs_engineering_research_produces_mult` apparaissent en clair dans
  les fichiers vanilla STI (`static_modifiers/02_static_modifers.txt`,
  `species_rights/06_species_rights_profiles.txt`) mais **TOUS commentés**.
  Vestiges Stellaris non portés en Star Trek: Infinite — l'engine STI ne sait
  PAS les évaluer et les marque "Invalid". Les traits species qui les
  référencent retournent des modifiers fantômes, ce qui corrompt l'état des
  pops puis casse le rendu d'entités au premier update.

  Fix : remplacement des 12 occurrences par `planet_jobs_research_produces_mult`
  (modifier générique research effectivement supporté par STI, utilisé dans
  `trait_intelligent` et 30+ traits species vanilla). Pour le trait Bajoran
  `trait_selective_researchers_bajoran` qui combinait 2 lignes drawback
  -10% chacune (-20% net), consolidation en une seule ligne -10% pour
  éviter la double pénalisation lors du collapse.

  Fichier modifié :
    common/traits/zz_cp26_minor_species_traits.txt   (12 lignes, 11 traits)
    Mod info/CP26_MINOR_SPECIES_TRAITS.txt           (doc HOTFIX en bas)

  → Effet en jeu :
     - Plus de "Invalid modifier" dans error.log au load.
     - Bonus research conservés en magnitude, généralisés (au lieu d'être
       fléchés society / physics / engineering).
     - Suppression du crash SIGSEGV au premier update entité.

[CRASH][HIGH] Radius galaxie 570 → 500 (limite engine hardcodée)
  Cause racine des crashes aléatoires SIGSEGV / EXC_BAD_ACCESS dans
  CConstructionQueueManager::DailyUpdate et CSaveGameTaskManager::
  CreateMemoryFiles (Mac et Windows — "access violation 0xc0000005" sous
  Windows, KERN_PROTECTION_FAILURE sous macOS).

  Diagnostic :
  Le moteur Clausewitz (commun à Stellaris et Star Trek: Infinite) impose
  une limite HARDCODÉE de radius <= 500. La doc officielle Paradox dit :

    "the map in Stellaris is a box 1000x1000x10, from -500 to +500"
    "Map radius (max 500)"
    "should be less than 500, preferably less than ~460"
    — Stellaris Wiki, Map_modding

  Au-dessus de 500, les structures spatiales internes du moteur
  (quadtree de proximity, grilles pathfinding, indices ConstructionQueue)
  débordent et provoquent des accès mémoire hors zone allouée. Le crash
  apparait au moment où un objet (constructeur, flotte, save serializer)
  tombe dans la zone fantôme — d'où le caractère aléatoire.

  État actuel CP26 :
    - Alpha-Beta_medium.txt : radius = 570  (HORS LIMITE)
    - tutorial.txt           : radius = 570  (HORS LIMITE)
    - Tous les autres scenarios : radius 300/400/450 (OK)

  Mesure géométrique : les 258 positions de systèmes ont une distance
  maximale de 405 depuis l'origine (hypot). Baisser le radius à 460
  garde TOUS les systèmes dans la box avec 55 unités de marge.

  Fix :
    - Alpha-Beta_medium.txt : radius 570 → 498 (engine hard cap exact)
    - tutorial.txt          : radius 570 → 498 (sync)
    - Camera limits inchangées (max abs = 450, déjà dans la box engine)
    - Hypot max système = 405, donc 95 unités de marge sous le cap engine.

  → Effet attendu : élimination des crashes aléatoires
    SIGSEGV/access-violation au runtime et au save. C'est la cause RACINE
    qu'on cherchait depuis le début. Mes diagnostics précédents (queue
    de construction "saturée par le ship_data dynamique", ConstructionQueue
    "corruption script") étaient des amplificateurs au mieux, pas la cause.
    Le radius était bien le problème.
