Session du 2026-05-14 (CRASH CPlanet — VRAIE cause : modifier invalide)
--------------------------------------------------------------------------------

[CRASH][CRIT] Restauration `common/pop_jobs/101_xl_map_reman_jobs.txt`
              et `common/scripted_variables/99_variables_xl_map.txt`.
              VRAIE cause des 4 crashs de la nuit (014804 / 015130 / 015307 / 015308).

  Symptôme dans error.log (présent à chaque démarrage depuis l'audit "final" du matin) :
    [modifier.cpp:2758]: Invalid modifier job_reman_job_add at file:
      common/districts/10_xl_map_remus_districts.txt line: 297

  Origine de la régression :
    Pendant l'audit "polish" du matin, j'ai supprimé deux fichiers en pensant
    qu'ils étaient silencieusement ignorés (parce que sans extension `.txt`) :
      - common/pop_jobs/101_xl_map_reman_jobs
      - common/scripted_variables/99_variables_xl_map
    FAUX. Le moteur Clausewitz charge les fichiers dans common/pop_jobs/ et
    common/scripted_variables/ INDÉPENDAMMENT de l'extension. Les supprimer
    a réellement retiré :
      - Le job `reman_job` (utilisé sur les districts Remus)
        → le modifier auto-généré `job_reman_job_add` n'existait plus
        → `10_xl_map_remus_districts.txt:297` référence un modifier invalide
        → daily update du planet manager lit un pointeur null/invalide
        → SIGSEGV puis cascade SIGABRT (heap corrupt)
      - Les variables `@dd_hp`, `@dd_evasion`, `@dd_build_time`
        (référencées par `common/ship_sizes/z_dderidax_herp_sizes.txt`)
        → ship_size Dderidax chargé avec valeurs par défaut (broken stats)

  Pourquoi le crash s'est aggravé avec les sessions :
    Le modifier invalide est dans un `triggered_planet_modifier`. Il est
    re-évalué à chaque recalcul de modifiers de la planète. Une partie qui
    dure (= les Remus ont des districts construits + pops affectés au job
    fantôme) augmente la fréquence d'évaluation → crash devient inévitable.
    Mes Phase 1 AI defines ont aggravé en faisant trembler la mémoire plus
    fort, mais ils n'étaient PAS la cause racine.

  Correctif :
    1. Restauration des 2 fichiers via `git show HEAD:<path>`
    2. Renommés en `.txt` pour pratique correcte (et évite de re-tomber dans
       le piège lors d'un futur audit)
    3. Fichiers présents :
       - common/pop_jobs/101_xl_map_reman_jobs.txt  (64 lignes, job `reman_job`)
       - common/scripted_variables/99_variables_xl_map.txt  (3 variables)

  Conséquence sur Phase 1 AI :
    Le rollback de Phase 1 reste en place (= conservateur). On verra
    plus tard pour réintroduire de l'agressivité IA progressivement
    UNE FOIS la stabilité confirmée sans le modifier invalide.

  Leçon retenue (pour l'agent et le futur) :
    Ne JAMAIS supprimer un fichier "qui a l'air mort" sans grep des
    symboles qu'il définit dans le reste du mod. Les jobs auto-génèrent
    des modifiers (`job_<name>_add`) qui peuvent être référencés
    ailleurs même si le fichier semble inutilisé.

  Crash dump : crashes/infinite_20260514_014611/exception.txt
  Signal 11 (SIGSEGV) → 6 (SIGABRT) en boucle (heap corruption).

  Stack trace :
    CGameState::DailyUpdate
      → CPlanetManager::DailyUpdate
        → CPlanet::DailyUpdateAllUnhabitableSelfDontReadOthers (parallel-for)
          → CJob::Wait → TaskSystem::TryStealTask → invoker → SIGSEGV
    (puis cascade __cxa_demangle dans AbortHandler — secondary crash)

    Le crash est dans le planet manager daily update — mais en réalité c'est

      - WAR_ATTACK_PLANET_PRIO=8 + AI_AGGRESSIVENESS_BASE=65 : recalcul wars
    → fleet objects invalidés mid-update → pointeurs stales lus en parallèle
       par le planet manager → SIGSEGV.

  Action :
    - Retrait des 9 defines de combat ajoutés en Phase 1.
    - Conserve Phase 2 (personalities = data tables passives, pas runtime).
    - Conserve les defines pré-existants (FLEET_GROUP_ABORT_MISSION_MULT,
      AI_NO_RETREAT_LIMIT, etc.) qui n'ont jamais causé de crash.

  Notes pour plus tard :
    Si on veut réactiver Phase 1, le faire UN define à la fois et tester

Session du 2026-05-14  —  Crash save SIGSEGV (cardassian entity duplicate)
--------------------------------------------------------------------------------

[CRASH][HIGH] Fix Cardassian .asset partial override — root cause crash save
              CConstructionQueue::WriteMembers
  Symptôme : crash signal 11 (SIGSEGV) à 00:50:59 lors d'une tentative de
  sauvegarde, ~9 minutes après le boot. Aucune erreur runtime entre 00:41:36
  et 00:50:59 dans error.log (logs s'arrêtent à la fin du boot).

  Stack trace propre côté sérialisation save :
    CSaveGameTaskManager::CreateMemoryFiles
      → CConstructionManager::CSerializer::WriteMembers
        → TPdxRefDatabase<CConstructionQueue, 8>::WriteMembers
          → CConstructionQueue::WriteMembers + 67   ← crash ici
            (offset bas = accès premier champ d'instance = pointeur invalide)

  Signaux discrets au boot (j'ai initialement minimisé ces warnings) :
    [00:41:33][pdx_entity.cpp:2579]:
      Duplicate of cardassian_01_governor_ship_entity added to entity system
    [00:41:33][pdx_entity.cpp:2579]:
      Duplicate of hideki_entity added to entity system

  Diagnostic complet :
  Les fichiers .asset sont chargés ADDITIVEMENT par le moteur Clausewitz —
  PAS via "last-loaded-wins" comme les common/ (game_singleobjectdatabase).
  Le moteur a une règle implicite : deux .asset du MÊME NOM dans le même
  path relatif sont traités comme "remplacement" (resolution par path),
  mais deux .asset de NOMS DIFFÉRENTS dans le même dossier sont chargés
  TOUS LES DEUX → si les entities ont les mêmes noms, le système d'entités
  garde 2 versions, les pointeurs internes se mélangent au rendu, et le
  heap se corrompt silencieusement.

  CP26 utilisait le pattern "fichier nommé différemment" :
    Vanilla : gfx/models/ships/cardassian_01/_cardassian_01_ships_entities.asset
              (25 entities, 1077 lignes)
    CP26    : gfx/models/ships/cardassian_01/zz_cp26_cardassian_01_ship_fixes.asset
              (2 entities = governor_ship + hideki, 111 lignes)
    → Les deux .asset sont chargés simultanément. Les 2 entities CP26 sont
      des DOUBLONS de leurs versions vanilla → warning pdx_entity.cpp:2579
      → corruption mémoire latente.

  Mécanisme du crash : la corruption affecte les pointeurs d'entities, mais
  les ConstructionQueues stockent des références à des objets qui ont eux-mêmes
  des liens vers le entity system. À la sauvegarde, le serializer traverse
  les queues et touche une référence qui pointe vers une zone heap réécrite
  par le doublon → SIGSEGV au moment du write.

  Pourquoi ce crash apparaissait "parfois" et pas systématiquement :
  Le doublon est créé au boot, mais le pointeur dangling n'est lu qu'au
  moment où une queue donnée référence l'entity côté serializer. Selon
  l'ordre des planètes/queues dans la database (qui varie d'une partie à
  l'autre selon les actions joueur), la queue corrompue peut être visitée
  tôt ou tard. Si elle n'est visitée qu'après que les pointeurs aient été
  réorganisés par d'autres allocations, pas de crash. Aléatoire effectif.

  Pourquoi maintenant et pas avant les modifs reduced fleet scale :
  Les recent count_owned_ship caps (18→15, 8→6) ont légèrement décalé
  l'ordre des opérations AI dans le tick, ce qui suffisait à déplacer la
  fenêtre temporelle où la queue corrompue est visitée par le serializer.
  Le bug .asset duplicate était PRÉSENT depuis l'introduction du fichier
  zz_cp26_cardassian_01_ship_fixes.asset, mais ne se manifestait pas dans
  toutes les configurations save.

  Pattern correct (déjà utilisé pour 5 autres ships dans le mod) :
  Copier le fichier vanilla _XXX_ships_entities.asset BYTE-PERFECT dans CP26
  sous le MÊME NOM (pas zz_cp26_), puis y appliquer les patches. Le moteur

    - cp26_capital_upgrade.1 retiré de on_game_start_country.
