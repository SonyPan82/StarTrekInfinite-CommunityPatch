CONTEXTE
--------
Le moteur Clausewitz crashe (SIGSEGV CConstructionQueueManager::DailyUpdate) quand
une colonie est initialisee avec `create_colony` suivie d'un `add_building` ou
`remove_building` sur le meme tick ou trop tot. Le vanilla evite ce pattern sur
ses colonies "bespoke" (Vulcan, Andor, Tellar, Khitomer) en utilisant directement
`set_owner` + `set_colony_type` + `add_building` sans passer par `create_colony`.

OBJECTIF
--------
Migrer TOUTES les colonies CP26 du pattern dangereux vers le pattern vanilla.

ETAT AVANT
----------
- create_colony + cp26_needs_capital_upgrade flag + deferred upgrade J+3
  (cp26_delayed_capital_upgrade.txt)
- 46 fichiers concernes

ETAT APRES
----------
- 0 create_colony dans CP26
- 0 flag cp26_needs_capital_upgrade
- cp26_delayed_capital_upgrade.txt supprime
- Toutes les colonies utilisent set_owner + set_colony_type + add_building direct

5. PROBLEME DETECTE DANS LES LOGS (a corriger)
--------------------------------------------------------------------------------

[00:57:04][effect_impl_pop.cpp:248]: Attempting to get a random pop species on
planet Glintara with no pops at file: scripted effect create_glintara_colony

Cause : create_glintara_colony utilise `species = romulan`. Sans le create_colony
precedent, la planete est vide au moment du create_pop. Le moteur ne peut pas
resoudre l'espece "romulan" sur une planete sans pops.

Fix propose :
- Remplacer `species = romulan` par `species = owner_main_species` dans
  01_romulus_glintara_effect.txt (set_owner a deja ete appele).
- OU ajouter 1 pop `owner_main_species` dans l'initializer avant create_glintara_colony,
  et reduire le while count de 11 a 10.
